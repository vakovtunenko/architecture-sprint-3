# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения
**Управление отоплением:**
- Пользователи могут удалённо включать/выключать отопление в своих домах через веб-интерфейс
- Пользователи могут устанавливать целевую температуру отопления через веб-интерфейс
- Пользователи могут просматривать состояние обогревательной системы (включена/выключена, текущая/целевая температура) через веб-интерфейс
- Система отправляет команды на включение/выключение/изменение целевой температуры обогревательной системе
- Система получает данные о состоянии с обогревательной системы

**Мониторинг температуры:**
- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс
- Система получает данные о температуре с датчиков, установленных в домах

Далее включаем фантазию тк по требованиям и описанию из задания нет возможности увидеть полную картину происходящего

**Регистрация устройств:**
- Специалисты по подключению могут регистрировать обогревательные системы, установленные в домах пользователей
- Специалисты по подключению могут устанавливать датчики температуры в домах пользователей
- Система получает данные о новом устройстве (обогревательная система/датчик температуры) в доме пользователя

**Регистрация пользователей:**
- Специалисты по подключению создают учетные записи пользователям при первом выезде к ним
- Система получает данные о новом пользователе

### 2. Анализ архитектуры монолитного приложения
- **Язык программирования**: Java
- **База данных**: PostgreSQL
- **Архитектура**: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения
- **Взаимодействие**: Синхронное, запросы обрабатываются последовательно
- **Масштабируемость**: Ограничена, так как монолит сложно масштабировать по частям
- **Развёртывание**: Требует остановки всего приложения

  - **Контекст: Сценарии автоматизации** - создание пользовательских сценариев, их хранение и выполнение

- **Поддомен: Управление отоплением**
  - **Контекст: Управление отоплением** - логика регистрации отопительных систем и датчиков температуры, включение/выключение, управление температурой, просмотр состояния и тд 
- **Поддомен: Управление освещением**
  - **Контекст: Управление освещением** - логика регистрации осветительных приборов, включение/выключение, настройка интенсивности освещения, просмотр состояния и тд 
- **Поддомен: Управление воротами**
  - **Контекст: Управление воротами** - логика регистрации электронных замков, отпирание/запирание, просмотр состояния и тд 
- **Поддомен: Наблюдение за домом**
  - **Контекст: Наблюдение за домом** - логика регистрации наблюдательных приборов, наблюдение и тд 

**Домен: Мониторинг и телеметрия**

  - **Контекст: Алертинг и реагирование** - реагирование на определенные показатели, алертинг пользователей

### **4. Проблемы монолитного решения**
- **Риски внесения изменений** - из-за большой кодовой базы и высокой связности компонентов при разработке нового или переработки старого функционала есть риск непредсказуемого влияния на всю систему, что может привести к появлению ошибок
- **Производительность** - повышенная нагрузка на часть системы может привести к ухудшению производительности всей системы
- **Сложность тестирования** - даже при внесении небольших изменений необходимо тестировать всю систему, что увеличивает трудозатраты
- **Сложность разработки** - из-за одновременной работы нескольких разработчиков над одной кодовой базой неизбежно будут возникать конфликты, что приводит к увеличению времени разработки и риску возникновения ошибок
- **Отказ системы** - в случае отказа одной части системы может начаться каскадный сбой всей системы, в результате чего вся она станет недоступной
- **Отсутствие гибкости в выборе технологий** - вся система использует единый стек технологий и нет возможности для определенной ситуации/функциональности использовать более подходящую технологию/язык/фреймворк
- **Масштабируемость** - нет возможности масштабировать *горячую* функциональность, только всю систему, что либо дорого, либо в определенных ситуациях даже не возможно
- **Деплой** - требуется перезапуск всей системы, во время которого она будет полностью недоступна, что негативно повлияет на пользовательскй опыт, а в каких-то случаях может быть даже опасным. Гипотетический кейс, пользователь не находясь дома случайно включил отопление на максимум, началось обновление системы и что-то пошло не по плану, система в простое на многие часы и пользователь ничего не может сделать с обогревательным устройством 
- **Время разработки и внедрения** - исходя из выше перечисленных проблем увеличивается время на цикл разработки и вывода нового функционала, что негативно отражается на бизнесе ввиду невозможности быстрой адаптации под новые рыночные условия
